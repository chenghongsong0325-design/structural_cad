# 加一條圖面硬規則

> ⚠️ 這是**工作流程**,不是 API 文件。數字(尺寸區間、常數)的唯一出處一律是
> 程式碼本身;這裡寫的是「怎麼做、會踩到什麼」。

使用者指正圖面問題時,**不要只修那一案**。這個專案的做法是把「什麼叫合格的圖」
寫成規則,讓以後所有的圖都不會有這個問題。規則放在
[src/design/layout/plan_check.py](../../src/design/layout/plan_check.py),
它是四條產線共用的品質底線。

## 第一步:判 error 還是 warning(判錯會讓產線無限重生)

- **error** = 同一份房間關係圖、**換個切法就能解決** → 擋圖重生
- **warning** = 非改設計(房間數/相鄰關係)不可 → 只回報,交給收斂迴圈餵給 LLM

判不出來就想:「重骰一個 seed 有沒有機會自己好?」有 → error;沒有 → warning。
判成 error 但落實端其實救不動,產線會一直重生到耗盡次數。

## 第二步:寫規則

1. 在 `plan_check.py` **檔頭 docstring** 的清單加一行(規則代碼 + 一句白話)。
   那份清單是規則的對外目錄,`/scan` 和 web 都照著它判讀。
2. 在 `check_floor()` 裡加一段,照既有編號註解的風格(`# ⑨ ...`),
   `issues.append(PlanIssue("error", "規則代碼", lb, 房間名, "白話說明"))`。
3. 訊息要**白話、可行動**,使用者會直接在網頁上看到(不合格會回 422 加這句話)。
4. 服務豎井要跳過:`if r.kind in VOID_KINDS: continue`(管道間/天井本來就沒門窗)。
5. **用 id 不要用房間名稱比對** —— 同一層可能有兩間「臥室」,用名稱會永遠修錯間。

## 第三步:驗收(四條產線都要,這步不能省)

新規則等於提高了全產線的門檻,**很可能打掛原本合格的圖**。順序:

```bash
# 1. 先看新規則抓不抓得到:拿那個壞掉的尺寸出圖
python scripts/preview_plan.py --width 6 --depth 12 --floors 3

# 2. 四條產線各掃一輪(區間見 [隨機掃描](scan.md),別自己背)
python scripts/scan_plans.py --n 60 --width 4,8 --depth 10.5,18   # 窄透天
python scripts/scan_plans.py --n 60 --width 5,9 --depth 5,9.4       # 淺基地
python scripts/scan_plans.py --n 40 --width 10,30 --depth 8,20      # 兩帶式

# 3. 全套測試(動 plan_check 不能只跑 not slow)
python -m pytest
```

- 掃描目標是**硬錯誤 0**。新規則掃出一堆命中 = 產線真的畫錯了,要回去**修骨架
  或修復器**,不是把規則放寬。
- 修完用**同一個 `--seed`** 重跑,確認該規則歸零、其他規則沒變多。
- AI 產線(`graph_layout`)不走 scan_plans,它有自己的 `design_loop`;
  改共用規則後也要出一張 AI 版的圖看過。

## 第四步:補測試 + 出圖

- 測試要**釘意圖,不要釘表象**。踩過的坑:有測試釘「文字等於『下』」「OTHER 圖層
  剛好 2 條線」,後來補標註時假性失敗 —— 釘的是當時的長相,不是規則要保證的事。
  正確寫法:造一個違反規則的 spec,斷言 `check_floor` 回得出那個規則代碼;
  再拿一個正常 spec,斷言它**不會**誤報。
- **測試不能為了通過而放寬既有斷言。**
- 收尾用 `/preview` 出圖,把 PNG 給使用者看 —— 他驗收的方式是看圖。

## 坑

- 規則加在 `check_floor`(單層)還是 `check_building`(跨層)要看它是不是需要
  上下層資訊(例:垂直核對齊)。單層能判的就別放 building 層。
- 門角淨距分級退讓 350/250/150/100 是**全產線共用**的既有常數,要用就引用,
  不要在新規則裡另寫一套數字。
- 加完記得回頭更新 [AGENTS.md](../../AGENTS.md) 的規則清單(它容易漏掉而過時)。
